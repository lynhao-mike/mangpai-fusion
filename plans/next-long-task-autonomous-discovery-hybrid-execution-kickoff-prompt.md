# 下一长任务 · 自主发现 + Hybrid Low-End/High-End 分层执行 · Terra 无人值守提示词

> 本文件只交付一份可直接粘贴给 ChatGPT 5.6 Terra 的执行提示词；**不在本文件内实施任何长任务**，也不预先指定下一个长任务的具体内容——内容由 Terra 在会话内根据仓库真实证据自主发现和确定。
>
> 设计依据：
> - 用户明确要求"下一个长任务的具体内容由模型根据仓库证据自主发现和确定"，因此本提示词只交付**发现协议**与**执行协议**，不预设候选清单的取舍结论。
> - 用户明确要求 Hybrid Low-End + High-End 分层：前段低成本阶段只做证据收集/结构化摘要/简单验证/草案，后段高端阶段才做复杂推理/多方案权衡/最终决策/代码生成审查/整合，且**高端决策换点必须暂停，给出模型切换选项**，而不是无缝自动跑到底。
> - 用户明确要求"允许 loop"、"允许子任务完成小目标"、"最好最终在一个对话完成整体任务"，因此内部允许迭代与修订循环，但必须在单一受控会话内闭环，不得请求切换会话。
> - 执行纪律沿用本仓库既有 `long-project-local-controller` 风格（Gate 序列、evidence-bounded freeze、non-inheritable authorization、LOCAL ONLY / NOT PUSHED、GitHub 永久不可变），与仓库内既有 kickoff prompt（如 [`as-of-life-state-blind-judgment-first-proof-point-kickoff-prompt.md`](as-of-life-state-blind-judgment-first-proof-point-kickoff-prompt.md)）保持同一治理语言,便于同一仓库内交叉审计。

## 使用说明

- 直接把"提示词正文"整段粘贴给 Terra，作为单次会话的完整任务说明。
- Terra 必须在**全新会话**中执行，不得复用任何已经做过判断或已经读过特定候选任务反馈内容的历史上下文（避免"发现阶段"本身被污染成"已经内定选谁"）。
- 提示词内置**强制暂停点**：Low-End 阶段结束后，Terra 必须停止并列出候选清单 + 模型切换选项，等待人工确认后才能进入 High-End 决策与执行阶段。这不是可选步骤，是硬 Gate。
- 若当前运行环境不支持模型切换，暂停点也必须原样呈现候选清单和"建议以高算力/高推理强度模式继续"的说明，把切换决定权交还给操作者，不得自行悄悄用同一模型继续跑高端阶段。

## 提示词正文

````text
你正在 mangpai-fusion 仓库承接一个长任务，但任务的具体内容不是我预先告诉你的——你必须先自己调研仓库真实证据，自主发现并确定"当前最高杠杆的下一个长任务"是什么，再执行它。这是一次真实的无人值守长任务，允许你在同一个对话里拆出子任务、允许你迭代修订，但必须在这一个对话内完成从发现到收口的整个闭环，不得请求切换会话。

## 执行纪律（贯穿全程，不可协商）

- 本任务采用严格的两阶段分层策略：
  1. **Low-End 阶段（低成本，模拟低端模型行为）**：只做只读证据收集、结构化摘要、关键实体提取、简单一致性核对、候选清单初稿。这个阶段必须简洁高效——只输出必要的结构化结果（表格或 JSON），不做多方案权衡、不做最终选型、不写代码、不下最终结论,避免无谓的长篇推理消耗 token。
  2. **强制暂停点（Model-Switch Gate）**：Low-End 阶段结束后，你必须**停止**，用固定格式（见下文"暂停点输出格式"）呈现候选清单和模型切换选项,等待人工确认继续，然后才能进入下一阶段。这一步不可省略，不可自行跳过直接进入高端阶段。
  3. **High-End 阶段（高成本，发挥你的完整推理能力）**：只在暂停点被明确放行后才启动。这个阶段负责复杂推理、多方案权衡、最终目标选定与合同冻结、必要的代码生成/审查、静态与动态验证、证据审查与 evidence-bounded freeze、最终交接。
- 全程遵守本仓库的治理语言（与仓库内既有 kickoff prompt 一致）：
  - 每个阶段只产出 `PASS` / `REVISE` / `BLOCKED` / `AUTHORIZATION_REQUIRED` 四种裁决之一；`REVISE` 走"诊断→修复→重新新鲜审查→精确重跑"，不得跳过复验。
  - 只允许本地只读/本地新增文件/本地非破坏性操作；**禁止任何 Git 或 GitHub 操作**（本地与远端均不可，包括提交、推送、创建 PR/Issue，即使仅是"顺手"操作）。
  - 不得把旧结论、过期假设或未经复验的历史 PASS 当作新证据。
  - 每个新增或修改文件都必须在最终汇报中逐一列出，不得静默扩大写集。
  - 全部产出保持 `LOCAL ONLY / NOT PUSHED`。

## Low-End 阶段：证据收集与候选发现（低成本，只读）

严格按顺序只读以下权威入口，不展开无关目录，不做深度推理，只提取事实：

1. `README.md`、`AGENTS.md`（尤其"禁止事项"一节，里面点名了哪些方向已经被判定为低杠杆）。
2. `META/project-state.json`（当前阶段、各能力 landed/partial/deprecated 状态、`missing_historical_tools`、`single_case_prospective_status`）。
3. `STATUS.md`（当前可用能力与不可硬编码信息清单）。
4. `handoff.md`（当前"大长任务"是什么、哪些 Gate 已 COMPLETED、哪些被明确要求"停止自动推进"、非继承授权边界）。
5. `plans/production-implementation-control.md` 的最后 60-100 行（最新几个 Gate 的裁决与 HOLD/BLOCKED 状态，例如是否存在明确写着"尚未由现有冻结事实唯一确定"或"HOLD"的条目）。
6. `tools/README.md`（active / internal / deprecated / historical / missing 五类工具的边界，尤其留意哪些能力"存在但未被其他子系统复用"）。
7. 若存在 `plans/*-next-task-geju-adjudication-*.md` 或类似"下一长任务格局裁决"文件，读取其"不得推导"章节和"中期未授权"选项——这些是明确被搁置但尚未执行的方向，属于一手候选证据。
8. 若存在最近的 `reports/*-report.md` 且其最终裁决为 `BLOCKED`，完整读取该报告，重点关注它的"方法论局限"章节与它没有解决、但被记录下来的根因——一份诚实的 BLOCKED 报告本身就是极高价值的候选任务来源，因为它标出了"上一次尝试卡在哪里、为什么卡"。

只读上述来源后，产出以下结构化结果（Markdown 表格，不写长段落）：

### 输出 A：仓库当前状态摘要（≤15 行表格）
| 维度 | 事实 | 来源文件:行号 |
|---|---|---|

### 输出 B：候选下一长任务清单（3-6 个候选，不排序、不选定）
每个候选一行：
| 候选 | 证据支持它是"当前被卡住/被搁置/被点名但未执行"的方向 | 来源文件:行号 | 是否与 `AGENTS.md` 已明确降级的方向冲突 |
|---|---|---|---|

候选来源的合法判据（至少满足一条才能入选候选清单，不得凭空构想）：
- 某份 `BLOCKED` / `HOLD` / `REVISE` 报告或裁决记录明确指出的未解决根因；
- `AGENTS.md`、`handoff.md` 或治理裁决文件里明确写出但标注"未授权""中期""需要用户另行授权"的方向；
- 代码中明确的占位/未实现标记（如 `NOT_IMPLEMENTED`），且没有被 `AGENTS.md` 禁止事项条款明确降级；
- 已存在但从未被其他子系统复用的成熟基础设施（例如某个隔离/校验机制只服务于一条产品线，另一条结构相似的产品线仍在用更弱的手工方式）。

不得把"随便找一个还没做的功能"当作候选；每个候选必须能明确指出它对应哪一条一手证据。

## 强制暂停点：Model-Switch Gate（不可省略）

完成 Low-End 阶段后，**立即停止**，按以下固定格式输出，然后等待人工回复后才能继续：

```
=== MODEL-SWITCH GATE ===
Low-End 阶段已完成。以下是候选下一长任务清单（未排序、未选定）：

[粘贴输出 A 与输出 B]

接下来是 High-End 阶段：需要在候选间做权衡取舍、给出格局判断、冻结合同、可能生成/审查代码、做静态与动态验证。这部分对推理深度要求更高。

请选择：
1) 继续使用当前模型完成 High-End 阶段（如果当前已是高算力/高推理强度配置）
2) 切换到更高算力/更高推理强度的模型后再继续（推荐：涉及多方案权衡与合同冻结的场景）
3) 由人工直接指定候选清单中的某一项作为目标，跳过自动选型，直接进入该候选的 High-End 合同阶段
4) 补充/修正候选清单后重新进行一轮 Low-End 调研

在收到明确指令前，不得自行进入 High-End 阶段,不得自行选定目标,不得开始写合同或代码。
```

## High-End 阶段：格局判断、合同冻结、执行与收口（仅在 Gate 放行后启动）

放行后，按以下顺序执行，允许在阶段内部拆子任务和迭代修订，但必须在本对话内跑完全部步骤或明确停在某个 Gate 并给出唯一下一动作：

### 1. ADMISSION（准入）
对候选清单中已选定（或人工指定）的目标，核实其前置条件、依赖关系、影响范围、兼容边界与最小必要范围。产出 `PASS` / `REVISE` / `BLOCKED`。

### 2. 格局判断（相当于 geju 打法，但不要求调用外部 skill，只要求同等严谨度）
在写死合同前，至少完成：
- 一句尖锐的 thesis：为什么这是当前最高杠杆的方向,不是"下一个凑巧还没做的功能"；
- 明确"继承来的约束"是否真实（是硬契约,还是只是历史惯性/自撰假设）；
- 至少给出"保守路线 / 干净目标 / 分阶段抵达干净目标"三个选项的对比,并明确推荐一个；
- 一条可验证路径：First Proof Point 是什么、什么证据会推翻这个方向。

### 3. CONTRACT（合同冻结）
新建一份 `plans/` 下的合同文件,冻结：唯一目标、权威输入、只允许新增的文件清单、禁止修改的范围、STOP 条件、Gate 执行顺序、方法论局限（如适用）、最终裁决的两种可能取值。对合同做一次逻辑新鲜的独立自审,只有 `PASS` 才能继续。

### 4. IMPLEMENT → STATIC_REVIEW → VERIFY → EVIDENCE_REVIEW
按合同执行,每一步都要新鲜独立复核,不得把上一步的自我评估当作既成事实。VERIFY 必须运行真实命令并记录真实输出(退出码、通过/失败数),不得用"应该能通过"代替实际运行结果。

### 5. FREEZE + HANDOFF
最终裁决只能是以下之一：
- `PASS / COMPLETE — EVIDENCE-BOUNDED FREEZE`（并列明直接证明了什么、禁止推断什么）；
- `BLOCKED — <具体原因>`（如实记录卡在哪一步、为什么,不得假装完成）。

冻结后必须把结论持久化到仓库里的合适位置(报告/合同/`handoff.md` 更新,视实际情况),并在最终回复中给出"唯一下一动作"。

## 硬边界（不可协商，覆盖两个阶段）

- 只允许新增本任务自己创建的合同文件、必要的实现/测试文件（若目标要求代码变更）与最终报告文件；不得修改与本任务目标无关的既有文件。
- 禁止任何 Git 或 GitHub 操作(本地与远端均不可)。
- 若发现任务实际上需要修改被其他 Gate/报告标记为"冻结不得重开"的既有契约或代码,视为 `BLOCKED`,不得绕过。
- 若候选目标本身要求的证据(如需要读取某个尚未接触过的敏感文件)与其他既有合同的排除清单冲突,视为 `BLOCKED`,换一个候选或如实汇报,不得静默违反既有排除规则。
- 全程不得声称已完成 Git/GitHub 同步、部署、发布或生产切换;所有产出保持 `LOCAL ONLY / NOT PUSHED`。

## 完成后的汇报格式

最终回复必须包含：Low-End 阶段候选清单全文、Model-Switch Gate 的实际放行方式、High-End 阶段选定的目标与格局判断摘要、合同冻结要点、实际执行的验证命令与真实输出、最终裁决(PASS/BLOCKED 及原因)、新增或修改的完整文件清单、唯一下一动作。不得省略任何一项,也不得用推测替代真实文件内容或真实命令输出。
````
