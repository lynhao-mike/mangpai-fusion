## 0. 本套指导文档的读者

本套文档面向具备强推理能力的执行模型（Opus 级别或同级）。每份指导文档都是**独立可执行的实施蓝图**，包含：目标、现状证据、接口契约、任务分解、验收标准、测试要求、风险与回退。执行者应能在不回看会话历史的前提下，仅凭单份文档 + 仓库源码开始工作。

所有升级单元共同服从两条铁律：

1. **不降低核心设计宪法的目标标准**，尤其是知识/代码分离、置信度绑定命题、可证伪才可概率化、流派允许克制、预测与反馈隔离。
2. **每个单元以已建成的评估框架 [`engine/evaluation/`](../../engine/evaluation/) 为唯一验收标准**，用盲测能力后验和门禁判断"是否真的变好了"，而不是主观感觉或规则数量。

## 1. 核心判断（为什么是这些方向）

2026-07-12 的 as-built 审计确认：系统的**分层契约与词汇已经是推理系统的样子，但运行内核仍是"串行工位 + 查表 + 事后线性微调"**。四个致命差距：

1. **L1 适用性不可学习** — 静态硬编码 `SCHOOL_PROFILES`，评估框架的能力后验无回流通道。
2. **L2 命题非引擎生成** — 有价值命题人工写入 JSON，盲测评估的是人而非系统。
3. **L6 仲裁无命理逻辑** — 只比置信数字，无分段裁决与矛盾对撞。
4. **L9 学习是拧螺丝** — 线性 alpha/beta，学不到条件化适用性知识。

**最高杠杆是接通 `评估 → L9 → L1` 回流飞轮**（升级单元 04）。但飞轮要成立，必须先有"共享命局特征向量"（01）、"引擎生成的真命题"（02）、"真实标注数据"（03）作为地基。

## 3. 依赖图与推荐执行顺序

```text
        ┌────────────────────────┐
        │ 01 命局特征向量层（脊椎）│
        └───────────┬────────────┘
                    │ 提供共享特征向量
       ┌────────────┼─────────────────────┐
       ▼            ▼                     ▼
┌─────────────┐ ┌───────────────┐   （04/06 也消费特征）
│ 02 命题引擎化│ │ 05 分段仲裁    │
└──────┬──────┘ └───────────────┘
       │ 提供引擎生成的真命题
       ▼
┌────────────────────────┐
│ 03 评估数据地基（真标注）│
└───────────┬────────────┘
            │ 提供真实盲测分数
            ▼
┌────────────────────────────────┐
│ 04 L1 可学习路由 + 回流飞轮（★）│
└───────────┬────────────────────┘
            │ 提供条件化能力更新需求
            ▼
┌────────────────────────────────┐
│ 06 L9 条件化学习与校准治理       │
└────────────────────────────────┘
```

**推荐顺序**：01（✅ 已完成）→ 02（✅ 两派最小闭环已完成）→ 03 → 04 → 05/06。

- **01 必须最先**：它是 02/04/05/06 共享的输入，缺它则各层各自造特征、无法条件化。
- **02 先于 03**：命题不是引擎生成，评估的就是人的水平，03 的标注数据会失真。
- **03 先于 04**：没有真实盲测分数，04 的"学过之后更准"无法证伪。
- **05 可与 03/04 并行**：分段仲裁只依赖 02 的命题结构，不依赖回流飞轮。
- **06 最后**：条件化学习依赖 04 的路由框架和 03 的数据分布。

## 4. 全局验收纪律

任何单元宣称完成前，必须满足核心路线 §4 的 GO 通用要求：

1. 预测冻结且无标签泄漏；
2. 推理轨迹可追溯；
3. 概率可追溯到评分样本与能力快照；
4. 与旧流程或固定基线同案盲测；
5. 误差、校准、高风险假阳性均被评估；
6. 失败案例已分类，不以删除异常样本掩盖问题。

并遵守评估框架已固化的安全默认：全部后验 `N_eff < 5` 强制 HOLD；高风险任务不可评估则门禁不安全；报告端从基础事实重算 gate，不信任注入值。

## 4B. 推荐执行顺序（有时间标注的行动路径）

按依赖关系和风险降低原则排序：

| 步骤 | 指导文档 | 可否并行 | 完成前提 |
|---|---|---|---|
| ① | [03 评估数据地基](03-evaluation-data-foundation.md) | 可与①并行 | 无 |
| ① | [01 命局特征向量](01-chart-feature-vector.md) | 可与①并行 | 无 |
| ② | [02 L2 命题引擎化](02-l2-claim-engine.md) | 串行 | 01 完成 |
| ③ | [04 L1 可学习路由 ★](04-l1-learnable-routing.md) | 串行（胜负手） | 01 + 02 + 03 全部完成 |
| ④ | [05 L6 分段仲裁](05-l6-staged-arbitration.md) | 可与④并行 | 02 完成 |
| ④ | [06 L9 条件化学习](06-l9-conditional-learning.md) | 可与④并行 | 03 + 04 完成 |

**起步建议**：03（标注数据）和 01（特征向量）是唯二无前置依赖的单元，建议并行启动——一边整理真实案例标注，一边建立命局特征向量层。

**阶段 ① — 地基**：03 + 01，并行启动，互不依赖
**阶段 ② — 脊椎上的引擎**：01 完成后启动 02
**阶段 ③ — 胜负手**：03 + 02 + 01 全部完成后启动 04；04 是整个路线的成败关键，用留出盲测集证明"学过之后 L1 分型命中率 > 静态基线"
**阶段 ④ — 换内核**：05（仲裁）依赖 02；06（学习）依赖 03 + 04；二者可在 04 产出数据后并行

每个单元完成后必须用已建成的 `engine/evaluation/` 框架做验收门禁，失败立即进入 HOLD 流程，不强行推进。

## 5. 隔离工作区约定

每个升级单元应在独立 git worktree + 分支执行（参考本仓库既有 SDD 流程），禁止直接改动：

- [`cases/`](../../cases/) 真实案例内容（03 的标注除外，且须走审计门禁）；
- [`theory/`](../../theory/) 生产规则（02 迁移须经判别力测试与人工审核）；
- [`META/`](../../META/) 机器状态；
- [`engine/domain-weights.yaml`](../../engine/domain-weights.yaml)、[`engine/expert-weights.yaml`](../../engine/expert-weights.yaml) 生产权重（只读为冷启动先验）。

## 6. 与现有评估框架的关系

[`engine/evaluation/`](../../engine/evaluation/) 是本套升级的**验收基座**，不是被升级对象。各单元应：

- 消费其 `BlindTask` / `CapabilityPosterior` / 四组实验作为验收信号；
- 通过其 CLI [`tools/school_capability_baseline.py`](../../tools/school_capability_baseline.py) 的 audit→freeze→score→report 链验证；
- 04 单元额外负责把 `CapabilityPosterior` 回流给 L1，这是评估框架当前缺失的唯一下游连线。
